Sistema de Cache

Redueix la càrrega a la base de dades i accelera l'aplicació guardant resultats costosos en memòria.

En aquesta unitat aprendràs:

  • Configurar backends de cache (LocMemCache, DatabaseCache, RedisCache) a CACHES
  • Usar l'API de baix nivell: cache.get(), cache.set(), cache.delete() i cache.get_or_set()
  • Cachear vistes completes amb el decorador @cache_page
  • Invalidar la cache automàticament amb signals quan canvien les dades

◆ Per a què serveix la cache i l'API de baix nivell

La cache és una capa d'emmagatzematge temporal molt ràpid (normalment en memòria RAM) que guarda resultats de consultes costoses per servir-los directament sense tornar a calcular-los. En Django, la cache és transparent: el teu codi llegeix d'ella com si fos qualsevol altra font de dades, i Django s'encarrega d'interconnectar-la amb el backend configurat.

El cas més habitual és cachear QuerySets que consulten moltes taules o fan agregacions complexes, i que el resultat no canvia gaire sovint. Per exemple, la llista de tots els autors d'una biblioteca pública canvia potser un cop al dia, però es consulta milers de vegades. Sense cache, cada pàgina visitada llança una consulta SQL; amb cache, la consulta es fa una sola vegada i el resultat s'emmagatzema.

Backend Entorn Característiques
LocMemCache Desenvolupament En memòria, per procés. No es comparteix entre workers. Perfecte per a tests i dev local.
DatabaseCache Dev / staging Guarda la cache en una taula SQL. Compartit entre workers, però més lent que Redis.
FileBasedCache Dev Fitxers al disc. Simple però lent per a producció.
RedisCache Producció Redis extern. Ràpid, compartit entre tots els workers, amb TTL natiu. Estàndard de la indústria.
MemcachedCache Producció Alternativa a Redis. Menys funcionalitats però molt madur.
  • cache.set(clau, valor, timeout) — guarda valor sota clau durant timeout segons. Si timeout=None, no caduca mai.
  • cache.get(clau, default=None) — recupera el valor. Si no existeix o ha caducat, retorna default.
  • cache.delete(clau) — elimina una clau de la cache. Útil per invalidar quan les dades canvien.
  • cache.get_or_set(clau, callable_o_valor, timeout) — retorna el valor si existeix; si no, el calcula (cridant el callable), el guarda i el retorna. Molt convenient per evitar el patró get/set manual.
  • cache.clear() — esborra tota la cache. Usar amb precaució en producció.
  • cache.set_many({'k1': v1, 'k2': v2}, timeout) — guarda múltiples claus d'una sola vegada (més eficient que múltiples set()).
  • KEY_PREFIX — prefix afegit a totes les claus d'aquesta configuració de cache. Útil per separar entorns (dev/prod) o aplicacions que comparteixen el mateix servidor Redis.
  • TIMEOUT — timeout per defecte en segons quan no n'especifiques cap (per defecte 300 s = 5 minuts).
⚠️ Cache i dades d'usuari

No cachis mai dades específiques d'un usuari sense incloure l'ID de l'usuari a la clau de cache. Si caches la pàgina de perfil sense distingir per usuari, tots els usuaris veuran el perfil del primer que l'ha carregat. Usa f"perfil_{request.user.id}" com a clau.

        'LOCATION': 'bibliapp-dev',  # nom intern per distingir instàncies
        'TIMEOUT': 300,
        'OPTIONS': {
            'MAX_ENTRIES': 1000,  # màxim d'entrades en memòria

}


# ===== settings/prod.py — Redis en producció =====
import os

CACHES = {
    'default': {
        # django-redis és el paquet de facto per a Redis amb Django
        'BACKEND': 'django_redis.cache.RedisCache',
        'LOCATION': os.environ.get('REDIS_URL', 'redis://localhost:6379/1'),
        'TIMEOUT': 300,
        'KEY_PREFIX': 'bibliapp',   # evita col·lisions si compartim servidor Redis
        'OPTIONS': {
            'CLIENT_CLASS': 'django_redis.client.DefaultClient',
            'SOCKET_CONNECT_TIMEOUT': 5,   # segons per connectar
            'SOCKET_TIMEOUT': 5,            # segons per operació
            'IGNORE_EXCEPTIONS': True,      # si Redis falla, comportament normal (sense cache)
        },
    }
}

# django-ratelimit pot usar la mateixa cache
RATELIMIT_USE_CACHE = 'default'


# ===== Exemple d'API de baix nivell =====
from django.core.cache import cache

# Guardar un valor durant 10 minuts
cache.set('total_llibres', 342, timeout=60 * 10)

# Recuperar (retorna None si no existeix o ha caducat)
total = cache.get('total_llibres')
if total is None:
    total = Llibre.objects.count()
    cache.set('total_llibres', total, timeout=60 * 10)

# Patró més net amb get_or_set:
total = cache.get_or_set(
    'total_llibres',
    lambda: Llibre.objects.count(),  # callable: s'executa només si cal
    timeout=60 * 10,
)

# Invalidar quan sabem que les dades han canviat
cache.delete('total_llibres')

# Guardar múltiples claus alhora (una sola connexió a Redis)
cache.set_many({
    'total_llibres':  Llibre.objects.count(),
    'total_autors':   Autor.objects.count(),
    'total_lectors':  Lector.objects.count(),
}, timeout=60 * 5)

◆ @cache_page, invalidació amb signals i vary_on_headers

El decorador @cache_page(timeout) és la manera més ràpida de cachear una vista completa: Django guarda la resposta HTTP sencera (headers inclosos) i la serveix directament en peticions posteriors sense executar la vista. És ideal per a pàgines de contingut públic que no canvien sovint, com una llista de llibres o la pàgina d'inici.

La invalidació és la part més delicada de la cache: saber quan esborrar les dades emmagatzemades perquè no serveixin informació desfasada. La millor estratègia és invalidar automàticament usant signals: quan es crea o modifica un model, el signal post_save neteja les claus de cache relacionades. Així la cache sempre té dades fresques sense necessitat de configurar un TTL molt curt.

  • @cache_page(timeout) — decorador per a vistes FBV. Per a CBV, usa method_decorator o afegeix-lo a urls.py amb cache_page(60)(vista).
  • vary_on_headers('Accept-Language') — indica a Django que mantingui versions de cache separades per a valors de header diferents. Útil per a multiidioma o per a respostes que varien segons Accept.
  • vary_on_cookie('sessionid') — manté caches separades per a cada sessió (és a dir, per a cada usuari autenticat).
  • cache_control(no_cache=True) — desactiva la cache per a una vista concreta, fins i tot si hi ha un middleware de cache global actiu.
  • never_cache — decorador que afegeix headers HTTP per evitar que qualsevol cache intermèdia (CDN, proxy) guardi la resposta.
  • Invalidació per patró — si uses django-redis, pots esborrar totes les claus que comencin per un prefix amb cache.delete_pattern("prefix_*").
📌 Cache en tests

Als tests, usa from django.test.utils import override_settings per substituir el backend de cache per DummyCache (que no guarda res) o per LocMemCache (que es buida entre tests). Així els tests no s'interfereixen entre si per dades cached.

Python views.py + signals.py — cache de QuerySets amb invalidació automàtica 
# ===== views.py =====
from django.shortcuts import render
from django.views.decorators.cache import cache_page, never_cache
from django.core.cache import cache
from .models import Llibre, Autor

# Clau de cache centralitzada per evitar errors tipogràfics
CACHE_KEY_LLIBRES = 'bibliapp:llista_llibres'
CACHE_KEY_AUTORS  = 'bibliapp:llista_autors'


def llista_llibres(request):
    """
    Vista de llistat de llibres amb cache manual.
    Usem cache manual (en lloc de @cache_page) per tenir control
    total sobre la clau i poder invalidar-la des dels signals.
    """
    llibres = cache.get(CACHE_KEY_LLIBRES)

    if llibres is None:
        # Cache miss: consultem la base de dades i guardem el resultat
        llibres = list(
            Llibre.objects.select_related('autor')
                          .filter(disponible=True)
                          .order_by('titol')
        )
        # Guardem durant 5 minuts
        cache.set(CACHE_KEY_LLIBRES, llibres, timeout=60 * 5)

    return render(request, 'bibliapp/llista_llibres.html', {'llibres': llibres})


# @cache_page: manera més simple per a vistes que no necessiten invalidació manual
@cache_page(60 * 15)   # cache durant 15 minuts
def portada_publica(request):
    """
    Pàgina de portada pública: canvia poc, @cache_page és suficient.
    Django guarda la resposta HTTP completa indexada per URL.
    """
    llibres_destacats = Llibre.objects.order_by('-data_creacio')[:6]
    return render(request, 'bibliapp/portada.html', {'llibres': llibres_destacats})


@never_cache
def tauler_personal(request):
    """
    Tauler personal de l'usuari: mai s'ha de cachear perquè és dada privada.
    @never_cache afegeix headers Cache-Control: no-cache, no-store, must-revalidate
    """
    prestecs = request.user.perfillector.prestecs.filter(retornat=False)
    return render(request, 'bibliapp/tauler.html', {'prestecs': prestecs})


# ===== signals.py — invalidació automàtica de cache =====
from django.db.models.signals import post_save, post_delete
from django.dispatch import receiver
from django.core.cache import cache
from .models import Llibre


@receiver(post_save, sender=Llibre, dispatch_uid='invalidar_cache_llibres_save')
@receiver(post_delete, sender=Llibre, dispatch_uid='invalidar_cache_llibres_delete')
def invalidar_cache_llibres(sender, **kwargs):
    """
    Quan es crea, modifica o esborra un Llibre, la cache de la llista
    queda desfasada i cal eliminar-la perquè la propera petició
    la regeneri amb les dades actuals.
    """
    cache.delete(CACHE_KEY_LLIBRES)
    # Si usem django-redis, podem esborrar totes les claus del patró:
    # cache.delete_pattern('bibliapp:llista_*')
Python views.py — get_or_set i vary_on_headers 
from django.shortcuts import render
from django.views.decorators.vary import vary_on_headers, vary_on_cookie
from django.core.cache import cache
from .models import Autor


def llista_autors(request):
    """
    get_or_set: manera compacta i segura de cachear un QuerySet.
    Si la clau no existeix, executa el lambda, guarda el resultat i el retorna.
    Si la clau existeix, el lambda NO s'executa (lazy evaluation).
    """
    autors = cache.get_or_set(
        'bibliapp:llista_autors',
        lambda: list(Autor.objects.order_by('cognom', 'nom')),
        timeout=60 * 5,  # 5 minuts
    )
    return render(request, 'bibliapp/llista_autors.html', {'autors': autors})


@vary_on_headers('Accept-Language')
@cache_page(60 * 10)
def portada_multiidioma(request):
    """
    vary_on_headers fa que Django mantingui una versió de cache
    per a cada idioma. Sense vary_on_headers, tots els usuaris
    rebrien la versió en l'idioma del primer visitant.
    """
    return render(request, 'bibliapp/portada.html', {})


@vary_on_cookie('sessionid')
@cache_page(60 * 2)
def recomanacions(request):
    """
    vary_on_cookie fa que cada sessió tingui la seva pròpia cache.
    Útil si les recomanacions depenen de l'usuari però el càlcul és costós.
    """
    recomanats = Autor.objects.order_by('?')[:5]  # exemple simplificat
    return render(request, 'bibliapp/recomanacions.html', {'recomanats': recomanats})
🔮 Cache múltiple

Django suporta múltiples backends de cache simultàniament. Pots tenir 'default' amb Redis per a dades generals i 'sessions' amb LocMemCache per a sessions. Accedeix a un backend no-default amb from django.core.cache import caches; caches['sessions'].get('clau'). A MediNetNode, la variable RATELIMIT_USE_CACHE apunta al backend de Redis per al rate limiting.

💡 El lambda dins de cache.get_or_set() ha de retornar una llista, no un QuerySet. Si guardes un QuerySet, Django el serialitza però pot donar problemes en deserialitzar. Fes lambda: list(Autor.objects.order_by(...)) per forçar l'avaluació i guardar una llista Python.

# books/views.py
from django.core.cache import cache
from .models import Autor

CACHE_KEY_AUTORS = 'books:autors_llista'
CACHE_TTL = 300  # 5 minuts

def llistar_autors(request):
    autors = cache.get(CACHE_KEY_AUTORS)
    if autors is None:
        autors = list(Autor.objects.annotate(
            total_llibres=Count('llibres')
        ).order_by('cognoms'))
        cache.set(CACHE_KEY_AUTORS, autors, CACHE_TTL)
    return render(request, 'books/llistar_autors.html', {'autors': autors})

# books/signals.py — invalidació automàtica
from django.db.models.signals import post_save, post_delete
from django.dispatch import receiver
from django.core.cache import cache
from .models import Autor

@receiver(post_save, sender=Autor)
@receiver(post_delete, sender=Autor)
def invalidar_cache_autors(sender, **kwargs):
    cache.delete(CACHE_KEY_AUTORS)

Cache per usuari amb clau personalitzada

De vegades la cache ha de variar per usuari (p.ex. pàgines personalitzades). @cache_page és massa simple; cal una clau de cache que inclogui l'usuari per evitar que un usuari vegi les dades d'un altre.

Tasques:

  1. Implementa cache manual a la vista els_meus_prestecs que cachi el resultat per usuari.
  2. Usa com a clau f"prestecs:{request.user.pk}" amb TTL de 2 minuts.
  3. Invalida la cache de l'usuari quan es crea un nou Prestec (via signal).
  4. Afegeix un indicador from_cache=True al context del template per saber si les dades vénen de cache.

@login_required
def els_meus_prestecs(request):
    cache_key = f"prestecs:{request.user.pk}"
    dades = cache.get(cache_key)
    from_cache = dades is not None

    if not from_cache:
        dades = list(Prestec.objects.filter(
            lector=request.user.lector
        ).select_related('llibre').order_by('-data_prestec'))
        cache.set(cache_key, dades, 120)

    return render(request, 'books/els_meus_prestecs.html', {
        'prestecs': dades, 'from_cache': from_cache
    })
