◆ CSRF, XSS i SQL Injection: com funcionen i com Django les mitiga

Les tres vulnerabilitats web més comunes tenen mecanismes de defensa molt concrets a Django. Entendre per què existeixen les proteccions és tan important com saber activar-les: és l'única manera de reconèixer quan una excepció a la regla és segura i quan no ho és.

Atac Com funciona Protecció de Django On falla
CSRF Un lloc maliciós fa que el navegador de la víctima enviï una petició autenticada al nostre servidor sense que la víctima ho sàpiga CsrfViewMiddleware + {% csrf_token %} @csrf_exempt mal aplicat; formularis sense el token
XSS L'atacant injecta codi JavaScript maliciós que s'executa al navegador d'altres usuaris Escapament automàtic de variables als templates Django Usar |safe o mark_safe() amb dades no fiables
SQL Injection L'atacant injecta codi SQL dins d'una consulta per llegir, modificar o esborrar dades arbitràries L'ORM de Django parametritza totes les consultes automàticament Usar .raw() amb f-strings o concatenació de strings

CSRF en detall: El middleware CsrfViewMiddleware genera un token secret per a cada sessió i l'incrusta als formularis amb {% csrf_token %}. En rebre una petició POST, verifica que el token del formulari coincideixi amb el de la sessió. Un lloc extern no pot conèixer aquest token, per tant no pot forjar la petició. @csrf_exempt desactiva aquesta protecció i només és acceptable per a endpoints que ja s'autentiquen per altres mecanismes, com les APIs DRF que usen tokens a la capçalera HTTP (on el disseny de l'arquitectura fa que el CSRF no apliqui).

  • {% csrf_token %} — tag obligatori dins de qualsevol formulari HTML que faci POST; genera un camp ocult amb el token
  • CSRF_COOKIE_SECURE = True — el cookie CSRF només es transmet per HTTPS; obligatori en producció
  • CSRF_TRUSTED_ORIGINS — llista de dominis fiables per a peticions cross-origin (necessari amb reverse proxies)
  • @csrf_exempt — usa-ho únicament quan tens un altre mecanisme d'autenticació per petició (token a capçalera, webhook amb signatura HMAC)

XSS en detall: Django escapa automàticament els caràcters especials HTML en totes les variables de template. Si un atacant aconsegueix guardar <script>alert('xss')</script> a la base de dades, Django el mostrarà com a text literal, no com a codi. El perill apareix quan els programadors sobreescriuen aquesta protecció o construeixen HTML dinàmicament de manera incorrecta:

  • {{ variable|safe }} — desactiva l'escapament; mai usar amb dades que provenen de l'usuari
  • mark_safe(string) — marca un string com a HTML segur; només per a strings que has construït tu, mai per a dades d'entrada
  • format_html() — alternativa segura a mark_safe quan cal construir HTML dinàmicament: escapa els arguments automàticament
  • JavaScript: mai inserir dades d'usuari via element.innerHTML; usar element.textContent que no interpreta HTML
  • JSON segur al template: usar {{ dades|json_script:"id-element" }} en lloc d'inserir dades directament a un bloc script

SQL Injection en detall: Quan escrius Llibre.objects.filter(titol=valor_usuari), Django usa consultes parametritzades: el valor s'envia separat de la consulta SQL, i el motor de base de dades el tracta sempre com a dada, mai com a codi. El risc apareix quan uses l'escape hatch de l'ORM per escriure SQL manual:

  • Llibre.objects.raw("SELECT * FROM llibres WHERE titol = %s", [titol]) — segur: paràmetres separats
  • Llibre.objects.raw(f"SELECT * FROM ... WHERE titol = '{titol}'") — perillós: concatenació directa
  • cursor.execute("SELECT * FROM llibres WHERE titol = %s", [titol]) — segur amb paràmetres
  • .extra(where=["titol = '%s'" % titol]) — perillós: el %s aquí és interpolació de Python, no un paràmetre SQL
🚨 Regla absoluta

Si necessites escriure SQL manual amb .raw() o cursor.execute(), sempre usa la sintaxi de paràmetres amb llista separada: cursor.execute("... WHERE id = %s", [id_valor]). Mai useu f-strings ni concatenació de strings en consultes SQL. El motor de la base de dades garanteix el tractament segur quan els valors van en la llista de paràmetres.

Python config/settings/prod.py — settings de producció segurs complets 
# config/settings/prod.py
"""
Settings de producció per a bibliapp.
Tots els valors sensibles provenen de variables d'entorn via python-decouple.
Mai hardcodis claus, contrasenyes ni secrets al codi font.
"""
from .base import *
from decouple import config, Csv

# ─── Secrets i configuració bàsica ────────────────────────────────────────
SECRET_KEY = config('DJANGO_SECRET_KEY')  # mínim 50 caràcters aleatoris
DEBUG = False
ALLOWED_HOSTS = config('ALLOWED_HOSTS', cast=Csv())

# ─── Base de dades de producció ───────────────────────────────────────────
import dj_database_url
DATABASES = {
    'default': dj_database_url.config(
        default=config('DATABASE_URL'),
        conn_max_age=600,   # connexions persistents fins a 10 minuts
        ssl_require=True,   # exigir TLS a la connexió PostgreSQL
    )
}

# ─── HTTPS i Transport Security ───────────────────────────────────────────

# Redirigeix TOTES les peticions HTTP a HTTPS (codi 301)
SECURE_SSL_REDIRECT = True

# HSTS: indica als navegadors que bibliapp.cat SEMPRE és HTTPS.
# 31536000 = 1 any en segons. Activa'l progressivament:
# primer 300 (5 min), després 86400 (1 dia), finalment 31536000 (1 any).
# Un HSTS mal configurat pot fer el lloc inaccessible durant tot el període.
SECURE_HSTS_SECONDS = 31536000
SECURE_HSTS_INCLUDE_SUBDOMAINS = True   # aplica també a www., api., etc.
SECURE_HSTS_PRELOAD = True              # permet incloure el domini al preload list

# Evita que el navegador "endevini" el MIME type d'una resposta.
# Protegeix contra atacs de MIME type confusion (p. ex. un CSV tractat com a JS).
SECURE_CONTENT_TYPE_NOSNIFF = True

# Evita que la pàgina es carregui dins d'un
